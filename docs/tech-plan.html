# Muse 技术方案

一款极简即时渲染 Markdown 编辑器（对标 Typora），纯 macOS 原生实现。v1.3 把排版、列表缩进与任务复选框按 Typora 实机截图校准，图片与表格改为真机可见的呈现，引用块的竖条不再断在第一行。

macOS 14+Swift 6AppKit · TextKit 2SwiftUIswift-markdown

v1.3引用块连续性与任务复选框（2026-08-29）

appendBlockQuote 原先只在 BlockQuote 的首行产出一个 token，而 .museBlock 是绘制层按 fragment 读的——TextKit 2 里一个段落 = 一行 = 一个 fragment。于是第二行同时缺竖条、底色与折叠 > 的人，引用块在第一行就断了。现改为逐行产出，行号统一走 lineSpan(of:)，token 的行与 quoteLines 同源。顺带修掉嵌套引用的既有缺陷：旧代码每层 marker 都从 syntaxStart 起算，> > x 的两层指向同一个 >。已知残留：嵌套引用仍只画一条竖条、不额外缩进。

任务复选框按 Typora 实机截图实测重做，四项：任务标记不再随光标或拖选回显源码（它是可点击的控件，回显会让控件在编辑时消失、也让「点一下切换」失去落点；源码模式照旧逐字显示）；从 ☐/☑ 字形改为自绘圆角方框（12pt、圆角 2.5pt、描边 1.5pt/#808080、勾选填充 #3478F6 + 白勾、方框到文字 9pt）；复选框上换小手光标，范围直接取 taskCheckboxHitTarget()，变小手的范围恒等于点得动的范围；完成项不改文字颜色（实测 Typora 勾选行与未勾选行文字色相同）。

两条被实测推翻的做法记录在此，免得再走：系统控件不行——macOS 26 把 NSButton 未勾选态改成实心浅灰块，而 WebKit 画 input[type=checkbox] 用它自己那套仿平台绘制、并不实例化 NSButton；跟随 controlAccentColor 也不行——本机它解析为 #007AFF，与 Typora 的 #3478F6 差 52 个红色分量。236 tests / 12 suites 全绿。

v1.2排版与列表缩进对标 Typora（2026-08-29）

排版按 Typora 默认主题（github.css）校准：body 行高 1.6（CJK 折算 multiple 1.35）、段距 0.8em 折算 11pt、标题字号 [36/28/24/20/16/16] 且上下 margin 加大、hr 加粗到 2px、引用竖线 4px 浅灰。代码围栏改为带垂直内边距的圆角通宽背景：Theme.fenceParagraph 撑出段落间距，绘制层经 .museBlockRole 反向延伸背景并画单侧圆角。

列表改用 list-style-position: outside 模型：Theme.listIndentStep = 28，整块列表比正文靠右一步，marker 悬挂在这一步撑出的 padding 里。这推翻了 v1.0 的几何——让 depth 1 的正文列等于 0 会把 marker lane 挤进文本容器的左页边距，列表看着比正文更靠左；而且回显 -  需要 18pt 却没有余量，TextKit 2 钳掉负行起点后整行右移，点进/点出顶层列表每次都跳一下。

marker 横向落点改为墨迹右缘贴正文列，回归相应从「量左缘 + 几何盒」改为「量位图墨迹右缘」：三层 •/◦/▪ 字形宽度不同（实测 •→◦ 差 9pt），左缘的差里含字形宽度差，右缘才是几何契约。

v1.1图片与表格的真机修复（2026-08-29）

v1.0 声称的「图片行内呈现」与「表格只读呈现」在真机上都不成立。图片用 .attachment 实现，而它只在 NSAttachmentCharacter（U+FFFC）上成立——NSTextStorage 的属性修复会把它从任何其他字符上抹掉，而「只写属性、不改字符」不允许插入该字符，所以一个像素都画不出来。现改为：独占一行的图片用 minimumLineHeight 预留行高、由 MuseLayoutFragment 绘制，加载不到的画带目的地文字的虚线占位框；MuseDocument.fileURL 的 didSet 把文档目录送到 RenderCoordinator.imageBaseURL，相对路径不再一律解析失败。

表格旧实现只是「等宽字体 + 通宽底色」，而等宽字体并不能让中文/emoji/ASCII 混排对齐（实测 .monospacedSystemFont(13)：M 8.04pt、中 12.90pt、🎉 19.00pt——中 并不是 ASCII 的两倍）。不许改字符就不能插制表符去用 tabStops，TextKit 2 也没有 TextKit 1 的字形替换钩子，NSTextTable 只在 TextKit 1 下生效。现在列宽由属性层实测量出、以 .kern 落在结构区首字符上，格线由绘制层画。

M2连续输入渲染管线修复（2026-08-28）

RenderCoordinator 不再在第二次未落地编辑后退化成整篇装饰。pending dirty range 始终维护在当前正文的 UTF-16 坐标系，支持前方插入平移、重叠删除收缩、多处编辑合并，并只在对应 revision 成功应用后清空。

swift-markdown 的同步解析不合作响应取消，因此新增 8ms 输入 burst 去抖；零间隔 11 键只启动一次最新快照解析，避免多个已取消任务并行争抢 CPU。

新增 6 项坐标、结构、真实管线与 200KB 性能回归；186 tests / 10 suites 全绿。Release 实测 200KB 单键 54.0ms、连续 11 键最后一键 66.7ms，最终 dirty 仅 12 / 132171 UTF-16 单元。

M4第二批自动化完成（2026-08-28）

列表 Enter 支持续项、任务状态继承、有序源码序号保持与空项退出；第二批新增多层缩进、引用内任务项和连续有序列表回归，插入新项不会重排后续兄弟项。

反引号 pair 可逐次升级为任意长度；包裹选区时按内容里的最长反引号 run 加一，选择最短安全 delimiter。三反引号、四反引号与波浪线围栏（含 info string）均验证不会在围栏体内误注入列表 marker。

任务 checkbox、列表与 pair 均补齐 redo；marked text 期间智能换行回退给系统；可访问值保持完整 Markdown 源码。没有引入新依赖，180 tests / 10 suites 全绿。M4 仍保持进行中，剩余真实中文 IME、真实窗口 checkbox 与 VoiceOver 人工 gate。

M3光标交互收口（2026-08-28）

方向键、鼠标命中和选区继续由系统 NSTextView 负责；Muse 只读取系统选区并更新 marker 派生属性。跨行选择会回显所有相交块的源码 marker。

新增“显示 → 源码模式”与 ⌘/。模式切换复用唯一 NSTextStorage，不改字符、不标脏、不进入 undo；输入法 marked text 期间延后属性应用。

Debug、Release 均为 120 tests / 8 suites 全绿；真实窗口已验证方向键穿越 marker、鼠标命中、跨行选区、源码编辑与撤销。M0-3 的完整中文 IME 与 VoiceOver 人工 gate 仍需继续关闭。

00本轮视觉复查（2026-08-27）

本轮对照截图复查发现并修复了四项列表视觉缺陷：

  1. 软换行列表项的一个 paragraph fragment 覆盖多条 NSTextLineFragment。旧实现按整个 paragraph fragment 的高度居中 marker，导致 marker 落在段落中部；现改为锚定首个 textLineFragments.first。
  2. 二级无序 marker 虽然由 AST depth 选择 ◦，字体 fallback 仍可能把 U+25E6 画成实心点。现在由 .museListDepth 驱动 glyph 判定，并在 fragment 绘制层用矢量实心圆、空心圆和方块，确保二级中心留空；绘制层不从源码缩进重新推导 depth。
  3. 首行行框包含 glyph 上下方的 leading；把较小字号 marker 居中到 typographicBounds 会使圆点和序号整体高于正文。现在读取首个 line fragment 的 glyphOrigin.y：有序序号与 checkbox 按 marker font ascender 对齐正文 baseline，无序矢量符号对齐正文 font 的 x-height 视觉中心，不使用固定像素补偿。
  4. 有序 marker 旧按自身宽度从正文列向左回推，等同于右对齐；1. 与 2. 的可见左边界会受字形 side bearing 影响，也无法与无序 marker 共用稳定左边界。现在用段落缩进推导固定 marker 槽，按 Core Text glyph path bounds 补偿可见墨迹左边界；多位序号在槽内适配且不移动正文列。

任务 checkbox 的 checked marker 使用系统 accent 色，unchecked marker 使用 secondaryLabelColor，两者都按浅色/深色外观解析。本轮只完成颜色与绘制，不实现点击切换；checkbox 点击将留到 M4，并通过标准文本编辑把 [ ]/[x] 替换为一次可撤销的源码操作。

本轮新增 6 项真实 TextKit 2/位图回归测试；最新 Debug 全量证据为 109 tests / 7 suites，其中 RendererTests 为 33 项。这组证据验证了首行锚定、无序 marker 的 x-height 对齐、有序 marker 的 baseline 与固定槽位、1./2. 的可见墨迹左边界、98./99./100. 不侵入正文、一级实心与二级空心的实际 fragment 像素，以及任务 checkbox 的外观颜色。

根任务以独立 bundle 启动 Debug App 做了视觉人工复查，已确认长列表 marker 位于第一视觉行、无序 marker 与正文 x-height 居中、有序序号与正文基线一致、二级 marker 明确为空心、checked checkbox 使用蓝色强调而 unchecked checkbox 使用灰色轮廓。本结果只覆盖本轮列表/checkbox 外观，不等同于 M0-3 的 IME、VoiceOver、零宽 marker、完整外观热切换等清单已全部完成。

01结论

技术路线保持不变：使用 AppKit 的 NSTextView（TextKit 2）作为编辑核心，SwiftUI 作为应用外壳，swift-markdown 负责 Markdown 语义解析。

实现边界
  1. NSTextStorage 是编辑期唯一可变文本；NSDocument 不维护第二份可变正文。
  2. 保存内容永远是完整 Markdown 源码；AST、token、渲染属性、图片与主题都是派生状态。
  3. swift-markdown 负责语义 AST，TokenScanner 只补编辑中的未闭合语法。
  4. SourceIndex 显式转换 UTF-8 源码位置与 UTF-16 NSRange。
  5. marker 零宽布局必须先通过 M0 的选区、换行、IME 与辅助功能验证。
  6. undo/redo 只记录源码修改；文本撤销后重新生成渲染。
  7. MVP 可整篇解析，但解析运行在不可变快照上，并用 revision 淘汰过期结果。

工作量：可演示 MVP 约 6～8 周全职；达到可长期日用的稳定程度约 8～12 周。M0 是开工 gate，而不是里程碑末尾的补测。

数据所有权

  • EditorBuffer.textStorage：所有键入、粘贴和行为命令的唯一正文。
  • MuseDocument：拥有 EditorBuffer，从 textStorage.string 生成保存快照。
  • RenderSnapshot：纯值派生数据，不负责保存，也不进入 undo。
  • SwiftUI：只保存文件名、主题、侧栏可见性等 UI 状态。

编辑流

textDidChange → revision + 1 → String 快照
→ 后台解析 AST、token、SourceIndex
→ RenderSnapshot → MainActor 检查 revision
→ 批量应用最新结果

04核心难点与对策

4.1 源码区间：UTF-8、UTF-16 与 token

swift-markdown 的 SourceLocation 使用 1-based 行号和 UTF-8 字节列；AppKit 使用 UTF-16。SourceIndex 为每行缓存两套起点并执行边界检查。AST 负责语义与精确源码区间，TokenScanner 只补编辑中的未闭合语法；RenderEngine 最终只接收 UTF-16 NSRange。

4.2 marker 隐藏与光标回显

marker 字符始终保留，只改变视觉属性。列表/任务 marker 使用近零宽属性，块级视觉则通过自定义 NSTextLayoutFragment 绘制。M0 必测中文、emoji、组合字符、嵌套强调、跨行选区、换行、鼠标、方向键和 VoiceOver。

任务 checkbox 是「跟随光标回显」的唯一例外：它是可点击的控件，光标经过就变回 - [ ] 源码会让控件在编辑时消失，也让「点一下切换」失去落点。源码模式仍然逐字显示——那条路与光标无关。

4.3 块级编辑行为

列表续行/退出、标题行为和保守自动配对均通过标准文本替换接口进入文档 undo manager。标题内容起点 Enter 在标题上方插入空段落并把光标留在那里，标题本体完整保留（引用内的标题会带上 > 前缀），空标题则退出标题。任务 checkbox 复用 fragment 的真实绘制几何命中，将源码 [ ]/[x] 标准替换为一次 undo 操作。自动配对尊重选区、转义、已有闭合符号与 marked text；使用 NSResponder 的命令入口（覆写 insertNewline(_:) 等）与标准替换入口，不吞掉所有 keyDown。属性尚未落地时的行归属回退到 swift-markdown 的单行解析（LineBlockKind，实测 14µs），不自己实现行级 CommonMark 规则。

4.4 中文输入法

hasMarkedText 为真时，不对 marked range 应用可能影响输入与布局的属性；上屏后再建立 revision。后台解析不能抢占主线程。人工矩阵覆盖拼音、双拼、五笔和系统英文输入，以及强调、链接、列表、代码围栏内的 Enter/Escape/方向键。

4.5 撤销 / 重做

undo 只包含源码变化；普通键入使用 NSTextView 原生 undo，自动配对和列表续行组成单个 undo group。主题、着色、marker 显隐与图片加载不注册 undo。撤销后重新生成 RenderSnapshot，不使用整篇字符串快照作为正式撤销模型。

4.6 并发与性能

主线程只负责输入、selection 与最新属性应用；后台任务解析不可变快照。旧任务可以取消，但正确性依赖 revision 校验。属性更新优先限制在变化块和可见区域，不把“下一 runloop”当作性能保证。

文档规模输入主线程预算目标
20KB< 8ms P95无可感知延迟
200KB< 16ms P95连续输入不丢帧、不跳光标
1MB不阻塞输入允许渲染滞后，源码编辑仍可用

200KB 不达标时，自建 block index，只重扫受影响块，并低频使用全量 AST 校准；不依赖 swift-markdown 的公开增量解析能力。

4.7 图片

NSTextAttachment 这条路是死的，不是「暂时不做」。.attachment 只在 NSAttachmentCharacter（U+FFFC）上成立：加在普通字符上时，NSTextStorage 的属性修复会在 endEditing 之后把它抹掉（不在编辑会话内则立刻就没），而「只写属性、不改字符」不允许插入 U+FFFC。回归守卫见 attachmentAttributeIsStrippedFromOrdinaryCharacter。

现在：独占一行的图片直接呈现在正文里——属性层用 minimumLineHeight 预留行高，MuseLayoutFragment 在撑高的行里画图，加载不到的画带目的地文字的虚线占位框，整段源码折叠。夹在正文中间的图片什么都不折叠：那一段不会被撑高去放图，折叠掉一半语法只会留下 ![标签 这种看起来像打错字的残句；整段源码保留、由样式层弱化成 marker 色，点击仍然弹预览（ImagePreview，支持相对文档目录、~ 与 http(s)）。相对路径的基准由 MuseDocument.fileURL 的 didSet 送到 RenderCoordinator.imageBaseURL——它必须每次渲染都传给引擎，因为块图片的呈现尺寸决定行高，是属性的一部分，不能等到绘制时才解析路径。

4.8 表格：列对齐只能靠 kern

源码里的表格列是按字符个数对齐的，而中文/emoji/ASCII 在任何字体下宽度都不成整数比——实测 .monospacedSystemFont(13)：M 8.04pt、中 12.90pt、🎉 19.00pt，中 并不是 ASCII 的两倍，等宽字体也救不了。既然不许改字符，就不能插制表符去用 tabStops；TextKit 2 也没有 TextKit 1 的字形替换钩子（NSGlyphProperty.elastic），NSTextTable 更是只在 TextKit 1 下生效。

所以列宽由属性层实测量出，以 .kern 落在结构区（| 与填充空白）的首字符上，把每一列撑到同一边界；绘制层按 .museTableColumns 画单元格边框、表头底色与隔行底色。TableStructure 只描述「源码里什么在哪」（单元格墨迹、结构区、列对齐），区间取自 swift-markdown 的 Table AST——不是第二套表格解析；TableLayout 负责需要读字体的排版度量。光标进入表格时回显源码且不画格线；分隔行整行作为块级 marker 随光标显隐。表格的可视化编辑仍留 Phase 2。

4.9 块级视觉：绘制层

列表圆点/序号/复选框、引用竖线、代码块背景和分隔线必须通过自定义 NSTextLayoutFragment 绘制。2026-08-27 截图复查发现：软换行 marker 不能按整个 paragraph fragment 高度居中，必须锚定首个 NSTextLineFragment 的真实 line geometry；二级无序 marker 不能只依赖字体 fallback 的 ◦，否则可能视觉上仍是实心点。当前实现由 AST 写入的 .museListDepth 驱动 glyph 判定，并用矢量实心圆/空心圆/方块绘制（矢量形状的墨迹盒由 ListMarkerGeometry.unorderedInkBox 统一给出，绘制与落点同源）。代码围栏的通宽背景经 .museBlockRole 反向延伸出段落间距、并只在首末行画单侧圆角。

列表 marker 的横向落点是墨迹右缘贴正文列（list-style-position: outside 模型）：Theme.listIndentStep = 28，深度 d 的正文列落在 d × 28，marker 悬挂在上一层与本层正文列之间那一步里。markerLaneWidth 只作为「宽到什么程度要缩字号」的预算，多位序号在预算内缩放且不移动正文列。正文列不能取 layoutFragmentFrame.minX（行首源码缩进已从行起点里扣掉，那是行起点不是正文列），而要向第一行问 marker 之后第一个字符的落点。

任务 checkbox 自绘圆角方框，几何与配色由 Typora 实机截图实测：checked 用 #3478F6 填充 + 白勾，unchecked 用 #808080 描边 + 白底，两者都按浅色/深色外观解析。不是 ☐/☑ 字形（字体回退下又细又方，圆角/勾形/填充都不可控），也不是系统控件（macOS 26 把 NSButton 未勾选态改成实心浅灰块，而 WebKit 画 input[type=checkbox] 用它自己那套仿平台绘制、并不实例化 NSButton）。落点、点击命中与小手光标区共用 ListMarkerGeometry.taskCheckboxBox，所以「变小手的范围」恒等于「点得动的范围」。完成项不改文字颜色。

块级视觉的回归断言必须经由 layoutManager 真实生产的 fragment，并落到位图像素上——例如三行引用必须有三个 fragment 各自自报引用视觉且都有墨迹，复选框两态用 marker 区域的均色而不是单点取样（方框正中会落在白勾上）。当前全量证据为 236 tests / 12 suites。

独立 Debug App 窗口的本轮列表/checkbox 外观人工复查已通过；完整 M0-3 的 IME、VoiceOver、零宽 marker 与外观热切换清单仍需逐项执行。
